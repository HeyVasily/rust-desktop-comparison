A desktop application, not a stripped-down window

The default examples include desktop integration. Light and dark palettes, following the OS at startup, and reacting while the application stays open are separate checks. A failed integration check does not mean a toolkit cannot draw a dark theme.

System appearance

Verify the OS setting, then check the client area at startup and through a light → dark → light transition in the same process. Linux needs a working settings portal or the appropriate native theme bridge.

External clipboard

Paste Unicode text from another process into the real filter, replace the system clipboard with a sentinel, then copy from the filter and compare the result. App-local simulated copy/paste is not sufficient.

Cost after actual use

Exercise theme and clipboard before measuring idle. Keep system fonts, accessibility support and the selected renderer enabled; record features, process scope and backend. Optional tray and global shortcuts remain a separate profile.

Historical UI-only idle memory

The 2026-11-09 matrix measured the application's whole process family (webview helpers included) with a 960×640 window, without exercising external clipboard or live theme changes. Metrics: Linux PSS, Windows private working set (Task Manager) and macOS physical footprint (Activity Monitor). Bars are the median of five runs on fresh VMs; the thin line spans the lowest to highest run. All panels share one scale.

How to read this. Each OS defines its metric differently, so compare toolkits within a panel. Linux PSS counts shared pages proportionally; Windows private working set excludes shared pages. These are not interchangeable with summed RSS (Tauri on Linux: 501 MiB summed RSS, 338 MiB PSS). Linux ran under Xvfb with software OpenGL, which GL-based toolkits (GTK 4.14, egui) pay for in private memory: the same GTK binary used 210 MiB PSS with OpenGL and 68 MiB with Cairo (experiment), and Qt rose from 23 to 73 MiB on native Wayland (X11 vs Wayland). Idle CPU stayed below 0.11 % of one core in this series — too small to rank. These are historical idle UI-only observations, not desktop-profile, startup, interaction or frame-rate measurements.

    Method and limits

    Historical matrix workload

    • 10 synthetic yards, 100 projects, filter and Refresh — no backend, no polling.
    • 960×640 visible content, release builds, one app at a time.
    • 30 s settling, then 120 samples; five runs, each on a fresh VM.
    • Theme startup only: the OS is switched to dark and every app relaunched.

    What it does not show

    • The cost of the current desktop-integrated builds or optional tray/shortcut integrations.
    • Live theme changes, external clipboard, screen-reader or IME acceptance in the historical series.
    • Startup time, interaction cost, frame rate or GPU rendering.
    • A controlled cross-OS ranking: runners, CPUs and toolkit builds differ.
    • Rust bindings for Qt: the Qt example is C++.
